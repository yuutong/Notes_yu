# 知识库的日常维护与网站发布

> 用固定流程完成记录、整理、验证和发布，让网站内容与本地知识库始终一致。

## 日常记录

新想法先进入 `inbox/`。这一阶段优先保证信息没有丢失，不要求一次写成完整文章。

建议至少记录：

- 暂定标题。
- 当时要解决的问题。
- 当前结论或下一步。
- 原始来源或上下文。

## 整理为正式笔记

每周或完成一个工作阶段后处理收件箱：

1. 搜索是否已有同主题权威页面。
2. 能补充旧笔记时不新建重复页面。
3. 确认主题目录和 YAML 属性。
4. 补充结论、示例、常见错误和来源。
5. 至少连接一篇上位主题和一篇相关笔记。
6. 内容稳定后将 `status` 改为 `evergreen`。

过期内容移动到 `archive/`；隐私或公司内部资料移动到 `private/`，不进入公开站点。

## 发布前验证

```powershell
npm run kb:build
npm run check
npm run audit
npm run kb:chat:test
```

只有以下结果全部满足时才发布：

- 需要格式化的 Markdown 为 0。
- 过期知识库输出为 0。
- 失效本地链接为 0。
- 重复权威正文为 0。
- 聊天检索和接口测试通过。

## 网站发布范围

GitHub 仓库中的静态内容会进入笔记网站，包括：

- Markdown 正文与图片资源。
- Docsify 页面、导航和搜索配置。
- 主题地图、质量报告和知识索引。
- 聊天界面的静态前端。

以下内容不应发布：

- `.env.local` 和任何 API Key。
- `private/` 中的个人或内部资料。
- Obsidian 的设备状态和缓存。
- 本地聊天记录。

## 静态网站与本地聊天的区别

Docsify 网站直接在浏览器中渲染 Markdown，适合公开阅读和全文搜索。GitHub Pages 不运行 Node.js 服务，因此网站上的聊天前端无法单独完成 AI 问答。

完整聊天在本机启动：

```powershell
npm run kb:chat
```

该命令同时提供 Docsify 网站和聊天后端。本机地址默认是 <http://127.0.0.1:3000/chat>。

## Git 发布流程

验证完成后，检查本次变更中没有敏感内容，再提交并推送到网站对应的远程仓库：

```powershell
git status
git add .
git commit -m "更新个人知识库"
git push origin master
```

推送完成只代表源文件已经上传。网站是否立即更新取决于 GitHub Pages 的构建状态和缓存，通常应再打开线上首页和一篇新笔记确认。

## 回滚原则

如果发布后发现问题：

- 内容错误：修正文档，重新构建并提交新的修复，不改写历史。
- 生成结果错误：修复构建脚本，不手工修改统计文件。
- 敏感信息泄露：先立即轮换凭据，再从当前版本和 Git 历史中清理。
- 链接错误：恢复兼容页或修复引用，然后运行全库审计。

## 维护节奏

- 随手记录：进入 `inbox/`。
- 每周：整理草稿、补链接、处理孤立页面。
- 每月：复核高频笔记的结论和来源。
- 每次发布：构建、检查、审计、测试、敏感信息检查。
