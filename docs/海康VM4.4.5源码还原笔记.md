# 海康 VisionMaster 4.4.50 源码还原：从计划到阶段验收

> 整理日期：2026-10-29。依据本机 `Applications\VMCode` 中的计划、源码和阶段报告整理；本文未重新执行测试。各数字是所注明日期的记录，不代表完整产品已通过验收。

## 1. 目标与软件结构

项目参照 KEYENCECode 的阶段化方法，将 VisionMaster 4.4.50 的安装目录作为分析对象，在独立的 `VMCode` 下整理源码、元数据和验证工具。目标是建立可重复编译、启动并验证功能的工程，以具体证据而非导出文件数量衡量完成度。

初始盘点得到 1,295 个 PE 文件，其中 657 个托管程序集、638 个原生文件。主程序是 WPF 托管应用；`Module(sp)` 的视觉模块通常由托管参数/UI 和原生算法适配层组成，`Server`、`ModuleProxy` 提供平台与宿主，后者还包含 Python 运行时。第三方库、资源和原厂算子运行库需要单独登记。

典型调用链为：托管控件与参数类 → PlatformSDK 的 `SyncSelfRun` → ModuleFrame / ModuleProxy → 原生模块适配层 → MVDAlgorithmSDK 算子 → CNN 推理运行库。项目利用 SDK 头文件、示例和 XML 描述确定接口；算子实现、推理引擎及 cuDNN 作为黑盒依赖，并未还原其内部源码。

## 2. 最初计划与实施顺序

`PLAN.md` 将工作划为 V00–V10：盘点及溯源、托管源码导出、编译基线、主程序离线运行、平台和 IPC、视觉模块、脚本与数据、通信、授权边界、辅助工具，最后进行产品级验收。每个阶段要求留下清单、日志或对照结果。扫描时排除输出目录、日志与转储；程序集记录来源、哈希、引用和 P/Invoke 边界。

识别、深度学习和注册学习另设 `PLAN-DL.md`。先以传统 OCR、CNN 分类、注册检测为样板，提取 SDK 接口和原生调用序列，再按家族推广到实际发现的 62 个模块。计划把模型、授权、宿主执行和数值对照列为独立验证环节。

## 3. 托管层：导出到编译基线

V00 建立 `inventory/binaries.json` 和 `managed-metadata.json`。V01 使用 ILSpy 导出依赖闭包、BAML 和资源，初始记录为 377 个工程、16,245 个 C# 文件及 1,102 个 XAML；产品源码和第三方依赖分别放在 `src`、`dependencies`。一个第三方设计器库存在资源导出问题，不能笼统视为完全成功。后续补入 N 型托管模块和 `CoordinateModuleCs`，所以不同报告的工程总数不同。

V02 使用 .NET SDK 与 .NET Framework 目标逐工程构建。早期基线从 211/377 提升到 299/377，随后通过修复 XAML、引用与反编译残件继续推进；计划中的后续快照为 339/377，主程序源码编译通过。常见问题包括 ILSpy 的 BAML 占位元素、WPF 类型及命名空间歧义、自引用造成的临时工程冲突、架构不匹配及缺失依赖。程序集引用图存在环，直接把所有 DLL 引用改成 ProjectReference 会连坐失败，因此需要分层处理循环引用。

编译成功并不等于重建后的主程序已经完成启动、工程保存重开及全功能回归；这些验收应以运行证据为准。

## 4. 原生视觉和 AI 模块

还原过程先确定 DLL 导出、vtable、参数通道和 `Process` 入口，再结合反汇编、SDK 头文件和模块 XML 建立输入、ROI、算子调用、结果封送及保存/加载链。公共行为按家族复用，模块差异留在各自适配层。生成的内核先做编译和工厂冒烟，再用真实计算或受授权限制的边界探针逐步验证。

2026-10-12 的模块清单记录：视觉 115 个，其中 113 个语义内核、2 个纯托管边界壳；识别/DL/注册学习 62 个，其中 43 个语义内核，19 个 N 型按 9 个平台适配型和 10 个纯托管型处置。共 177 个原生构建目标记录为编译及冒烟通过，156 个语义内核为视觉 113 加 DL 43。这里的“语义内核”指已接入相应调用和结果路径，并不意味着所有结果与原版数值一致。

专项记录还提取 134 个 SDK 头文件、611 个类和 4,459 个方法；注册学习协议和模型边界有独立报告。模型解析和许多算子需要 HASP 授权，项目保留运行时依赖，没有将加密模型或推理引擎内部当作已恢复源码。

## 5. 验证和进一步对齐

2026-10-12 总账记载统一验证包共 165 项：43 个 DL 内核、113 个视觉内核、9 个 VmTool 适配器。无狗环境下 17 项记录为真实计算及断言通过，148 项停在授权等边界，失败数为 0；视觉内核测试记录 112/112。边界返回只证明探针到达预期边界，不证明插狗后推理、结果封送或数值与原版一致。

验证工具曾发现全列表加载导致进程崩溃，且批处理的 `if errorlevel 1` 未捕获负退出码。后续改为逐模块子进程，并按实际退出码判定，避免测试静默通过。这一修正说明构建成功和测试程序退出成功都需要可核查的门禁。

10 月 12 日之后继续进行视觉 C++ 与 GUI 对齐：报告记录 111/111 个有完整 GUI 规格的工程构建通过；115 个视觉模块中部分原始 GUI 资产缺失。GUI 默认值覆盖与 `Process` 行为一致性是不同指标。视觉执行日志还记录 115 项 Save/Load 证据和部分 Display 静态通道覆盖；真实输出快照仍需有授权环境。

10 月 15 日 AI/DL 执行日志记录 43/43 个语义内核的 Process 入口证据、Save/Load 探针和无狗 ModuleFrame 快照；Display 静态检查覆盖 947/947，语义内核测试 43/43 通过。快照均停在边界返回码，下一步仍是逐家族核对调用序列、在授权环境取得真实输出并建立 golden 对照。静态通道覆盖不等于运行时输出正确。

## 6. 当前结论与后续工作

已有成果包括托管反编译和部分编译基线、视觉与 AI 原生适配层源码、模块矩阵、GUI 参数规格和分层验证工具。它们为继续复现和定位差异提供了基础，但现有记录不足以宣称完整产品已还原或与原版等价：平台宿主及算子仍依赖原厂二进制，148 项需要授权条件下重跑，真实服务器端到端、原版数值对照和完整产品工作流仍需证据。

下一步应在具备合法授权与对应模型的环境运行验证包，保存输入、环境、返回码与原版/重建输出，逐模块比较数值和图像；继续核对 Process 调用顺序和 GUI 行为，补齐缺失资产与托管边界，并进行工程保存重开、流程集成及残余二进制依赖审计。报告中的历史计划状态应与较新的日志、实际产物分别核对。
